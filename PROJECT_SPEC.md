# RAG-чатбот для технічної підтримки — технічне завдання

## Мета
Чатбот-консультант техпідтримки на основі RAG. База знань — набір інструкцій у HTML, що лежать локально в папці. Бот відповідає на запитання користувачів, спираючись виключно на ці інструкції, і показує джерела. Має бути можливість оновити базу знань при додаванні нових HTML-файлів.

Контекст: курсова робота (не продакшн). Пріоритет — простота, відтворюваність, чистий код. Проєкт буде викладено на GitHub.

## Фінальний стек
| Шар | Технологія |
|---|---|
| Очищення HTML | trafilatura (основне) + BeautifulSoup (доочищення) |
| Чанкінг | LangChain `RecursiveCharacterTextSplitter` |
| Embeddings | OpenAI `text-embedding-3-small` (опційно локальний `bge-m3`) |
| Векторна БД | ChromaDB (embedded, persist у файл) |
| Генерація (LLM) | Перемикач OpenAI ↔ OpenRouter (OpenAI-сумісний SDK) |
| Бекенд | FastAPI |
| Фронтенд | React + Vite |

## Архітектура
```
HTML-папка → [Indexing pipeline] → ChromaDB
                                       ↑
React UI ⇄ FastAPI ⇄ retrieval ⇄ ─────┘
                   ⇄ LLM (OpenAI / OpenRouter)
```
Бекенд має два модулі: **indexing** (побудова/оновлення бази) і **query** (пошук + відповідь).

## Порядок робіт
1. **Indexing pipeline (окремий CLI-скрипт).** Читає HTML з папки → чистить (trafilatura + BeautifulSoup) → чанкає (300–800 токенів, overlap 10–15%, ріже по структурі/заголовках) → рахує embeddings → пише в Chroma з метаданими: `source_file`, `title`, `section`, `content_hash`. **→ Після цього кроку обов'язково пройти Чекпоінт А (див. розділ «Перевірка якості») перед рухом далі.**
2. **Інкрементальне оновлення.** Хеш кожного файлу зберігається; при повторному запуску обробляються лише нові/змінені файли, старі чанки видаляються по `source_file`.
3. **Query-логіка.** Запит → embedding → пошук top-k у Chroma (k≈4–6) → збірка контексту → промпт до LLM. Системний промпт: відповідати лише на основі контексту, мовою користувача, чесно казати «не знаю» при відсутності інформації. Повертати джерела з метаданих. Поріг релевантності проти галюцинацій. **→ Після цього кроку пройти Чекпоінт Б (тест retrieval).**
4. **FastAPI.** Ендпоінти: `POST /chat` (запит → відповідь + джерела), `POST /reindex` (оновлення бази у фоні через BackgroundTasks), `GET /status` (стан індексації).
5. **React + Vite.** Дві сторінки: чат (поле запиту, відповіді, показ джерел) та адмін-панель (кнопка «оновити базу знань» + статус). Стрімінг відповіді — опційно, у другу чергу.

## Перевірка якості

Спершу попросити Claude Code написати **діагностичний скрипт** (статистика довжин + вивід випадкових чанків + кілька тестових запитів) — щоб після кожної зміни параметрів за секунди бачити, стало краще чи гірше.

### Чекпоінт А — після кроку 1 (очищення + чанкінг)

Очищення HTML:
- На вибірці 5–10 файлів різного типу (короткі, довгі, з таблицями, зі списками кроків) вивести очищений текст поруч з оригіналом.
- Зник «сміттєвий» текст: меню, навігація, футер, cookie-банери, кнопки.
- **Збереглася вся суть** — усі кроки інструкцій, таблиці, деталі (втрата корисного контенту гірша за залишене сміття).
- Слова й абзаци не злиплися (немає тексту без пробілів після видалення тегів).
- Заголовки секцій збережені, ієрархія читається (вивести лише заголовки кожного файлу).
- Прогнати ВСІ файли й вивести довжину тексту до/після очищення. Аномалії (лишилось 1% або 99%) — червоний прапорець.

Чанки:
- Гістограма/розподіл довжин чанків: більшість у діапазоні 300–800 токенів. Багато крихітних (~30 ток.) → надто дрібне різання; гіганти (~3000 ток.) → splitter не спрацював.
- Роздрукувати 15–20 випадкових чанків і прочитати: кожен читається сам по собі, крок інструкції не обірвано посеред речення/списку, overlap між сусідніми працює.
- Метадані кожного чанка коректні: `source_file`, `title`, `section`, `content_hash`.

### Чекпоінт Б — після кроку 3 (retrieval)

Головний тест якості пайплайну:
- Скласти 10–15 типових запитань техпідтримки, для яких відомо, у якій інструкції відповідь.
- Для кожного зробити пошук top-5 у базі.
- Успіх: у більшості випадків серед результатів є саме той чанк, де реально міститься відповідь.
- Якщо ні → проблема в чанкінгу (погані фрагменти) або в очищенні (контент загубився). Повернутися до Чекпоінта А, покрутити розмір чанка / overlap, переіндексувати, перевірити знову.

## Ключові вимоги та застереження
- **Якість чанкінгу вирішує все** — не дати кроку інструкції розірватися навпіл.
- **Метадані й джерела обов'язкові** — користувач має бачити, з якої інструкції взято відповідь.
- **Embeddings індексації та запитів — однією моделлю.** Провайдер embeddings прив'язаний до бази; вільний перемикач лише для генерації.
- **Безпека ключів:** `.env` у `.gitignore`, ніколи не комітити. Витрати на embeddings мінімальні (~$0.02 на 1M токенів).
- **README** оцінюється окремо: опис, архітектура (схема вище), інструкція запуску backend і frontend.
